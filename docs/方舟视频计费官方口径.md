## 一、计费公式（S2）

官方原文：

> - 视频价格估算公式：`token 单价 × token 用量`
> - token 用量估算公式：`(输入视频时长+输出视频时长) × 输出视频的宽 × 输出视频的高 × 输出视频的帧率/1024`
> - 上述 token 用量均为估算值，准确 token 用量以调用 API 后返回的 `usage.completion_tokens` 字段为准。
> - 仅对成功生成的视频计费。因审核等原因导致生成失败的，不收取费用。

帧率固定 24。本网关的 `relay/helper/video_token.go:EstimateSeedanceTokens` 与该公式一致。

两个容易漏掉的修正项：

- **样片（Draft）模式折算**：开启后 token 用量 = `估算用量 × 折算系数`。Seedance 1.5 pro 的系数为无声 0.7、有声 0.6，其他模型暂不支持。
- **最低 token 用量限制**：Seedance 2.0 系列与 2.5，当**输入包含视频**时，若估算用量低于最低用量，按最低用量计费。最低用量与分辨率、宽高比、输出时长有关，官方只提供[表格](https://bytedance.larkoffice.com/wiki/FXaYwxzJ5i5Zdik32ipcWzt7nxd?table=tblheIYDXXwYM43b&view=vew2CR2JYM)与计算器，未在文档正文中给出公式。

## 三、分辨率 × 宽高比 → 宽高像素值（S1）

**这张表不能自己推算。** 方舟按**恒定像素预算**分配，不是「短边钉在档位上、长边按比例推」。最典型的是 1:1：720p 下是 960×960 而不是 720×720，自己推会少算 44%。

下表 480p/720p/1080p 取 Seedance 2.5 列，4k 官方只有 Seedance 2.0 系列有值：

| 分辨率 | 16:9 | 4:3 | 1:1 | 3:4 | 9:16 | 21:9 |
|---|---|---|---|---|---|---|
| 480p | 854×480 | 752×560 | 640×640 | 560×752 | 480×854 | 992×432 |
| 720p | 1280×720 | 1112×834 | 960×960 | 834×1112 | 720×1280 | 1470×630 |
| 1080p | 1920×1080 | 1664×1248 | 1440×1440 | 1248×1664 | 1080×1920 | 2206×946 |
| 4k | 3840×2160 | 3326×2494 | 2880×2880 | 2494×3326 | 2160×3840 | 4398×1886 |

其他模型代的取值与上表略有出入（例如 Seedance 1.0 系列 480p 16:9 是 864×480、1080p 21:9 是 2176×928），完整四列见 S1。

**同一档位下各比例的像素总数几乎相等**：720p 及以上极差不到 0.7%，480p 不到 4.5%。所以宽高比认不出来时回退按 16:9 估算是安全的，偏差远小于一档分辨率之差。

> 需要更正一个曾经流传的说法：21:9 在 1080p 下**不是** 2560×1080，因此「21:9 少算 25%」「4:3 多算 33%」都不成立，实际偏差在 1% 以内。

## 四、参数取值与默认值（S1）

### resolution

可选值 `480p` / `720p` / `1080p` / `4k`。各模型支持范围与默认值：

| 模型 | 默认值 | 可选值 |
|---|---|---|
| Seedance 2.5 | 720p | 480p、720p、1080p |
| Seedance 2.0 | 720p | 480p、720p、1080p、4k |
| Seedance 2.0 fast / mini | 720p | 480p、720p |
| Seedance 1.5 pro | 720p | 480p、720p、1080p |
| Seedance 1.0 pro / pro fast | 1080p | 480p、720p、1080p |

### ratio

可选值 `16:9`、`4:3`、`1:1`、`3:4`、`9:16`、`21:9`、`adaptive`。

默认值：Seedance 2.5 / 2.0 系列 / 1.5 pro 均为 `adaptive`；Seedance 1.0 pro 与 1.0 pro fast 为文生视频 `16:9`、图生视频 `adaptive`（1.0 系列文生视频不支持 `adaptive`）。

Seedance 2.5 在**视频编辑、视频延长、首帧/首尾帧生视频**任务中仅支持 `adaptive`，不接受指定比例。

图生视频时若指定比例与输入图不一致，方舟会居中裁剪。

### duration / frames

- 单位秒。`duration` 与 `frames` 二选一，**`frames` 优先级更高**。
- `frames` 取值为 `[29, 289]` 区间内满足 `25 + 4n` 的整数（n 为正整数），帧数 = 时长 × 24。**仅 Seedance 1.0 pro 与 1.0 pro fast 支持**，其余模型只能用 `duration`。
- `duration = -1` 表示**由模型在有效区间内自选时长**。官方明确提示「视频时长与计费相关，请谨慎设置」。
- 查询接口返回的 `duration` 是约数：`实际总帧数 / 24` 向下取整。

各模型取值范围：

| 模型 | duration 范围 | 备注 |
|---|---|---|
| Seedance 2.5 | [4, 30]，默认 `-1` | 视频编辑任务仅支持 `-1` |
| Seedance 2.0 系列 | [4, 15]，或 `-1` | |
| Seedance 1.5 pro | [4, 12]，或 `-1` | |
| Seedance 1.0 pro / pro fast | [2, 12] | 不支持 `-1`；支持改用 `frames` |

### generate_audio

`boolean`，**默认值 `true`**——不传即生成有声视频。支持 Seedance 2.5、2.0 系列、1.5 pro。生成的有声视频均为单声道，与传入音频的声道数无关。

这个默认值直接影响 1.5 pro 的档位：有声 16.00 / 无声 8.00，差一倍。

## 五、本网关实现与官方口径的差距

### 已对齐

| 项 | 位置 |
|---|---|
| token 公式（含输入视频时长累加） | `relay/helper/video_token.go:EstimateSeedanceTokens` |
| 分辨率 × 宽高比像素表（逐格对齐官方） | 同上，回归测试 `TestVideoTokenPixelsMatchArkOfficialTable` |
| 计费维度 = 分辨率 × 是否含视频输入 / 是否有声 | `setting/billing_setting/video_token.go` 的 `_video` / `_audio` 变体 |
| 计费读到的分辨率、宽高比、时长与下发给上游的同源 | `relay/common/relay_info.go` 的 `RequestedResolution` / `RequestedAspectRatio` / `RequestedOutputSeconds` |
| `generate_audio` 官方默认 true 的模型，不传参数时按有声档计费 | `relay/channel/task/doubao/adaptor.go:pinGenerateAudio`，契约表 `constants.go:videoDurationLimits` |
| 统一协议的 `audio` 别名对齐到方舟原生的 `generate_audio`，冲突时以原生键为准 | `doubao/adaptor.go:alignAudioAlias` |
| `frames` 优先于 `duration`，按精确的 `frames/24` 秒计费，且不再重复下发 `duration` | `doubao/adaptor.go:ResolveVideoBilling` / `convertToRequestPayload` |
| `frames` 按官方 `[29,289]` 且 `25+4n` 校验，只放行 1.0 pro / pro fast | `doubao/adaptor.go:requestedFrames` |
| `duration = -1`（模型自选时长）按该模型时长区间上界预扣，靠 `usage` 差额结算 | `doubao/adaptor.go:requestedDuration`，上界表 `constants.go` |
| 显式 `duration` 按各代官方区间校验（2.5 [4,30]、2.0 [4,15]、1.5 [4,12]、1.0 [2,12]） | 同上。通用校验只拦到 3600 秒，不按代次拦会先按 3600 秒预扣再等上游拒绝 |
| 认不出上游模型（接入点 ID、不带代次的别名）时对时长与音频档 fail-closed | `doubao/adaptor.go:videoContractFor` / `pinGenerateAudio` |

`-1` 作为「由上游模型自选时长」的哨兵定义在统一协议里（`relaycommon.DurationSelfSelect`），
但通用校验默认拒绝，只有 `AllowSelfSelectedDuration()` 显式放行的适配器能收到——
放行给所有 platform 会让 `-1` 原样级联到不认识它的下游节点，那边按自己的默认时长预扣，
最终那个上游却按区间上界生成。

后几项经由 `channel.VideoBillingResolver` 接入：上游若能给出比请求里的 `duration` 更准的
实际生成秒数，由适配器在模型映射之后自己返回，通用规则不做假设；违反上游契约的取值
也在这里 400，而不是把一个计费乘数原样丢给上游去拒绝。

### 仍存在的差距

**先看清楚差额结算这道闸**，它决定了下面每一条的真实严重性。

Seedance 成功任务的终态响应必带 `usage`（`doubao/adaptor.go:ParseTaskResult` 直接读
`resTask.Usage.TotalTokens`），`service/task_polling.go:settleTaskBillingOnComplete`
据此按下单时快照的单价重算并多退少补。所以**按 token 计价的 Seedance，预扣估算的偏差
最终都会被官方 usage 修正**；预扣不准影响的是别的东西：

- 预扣偏高 → 余额刚够的用户被误拒 402；
- 预扣偏低 → 补扣时用户余额可能已耗尽 → 欠费。

三条例外不会走到这道闸：按次价（`PerCallBilling`，本就是固定价）、按秒档（$/秒与 token
不同量纲，下单时已定死金额）、以及上游没返回 usage 的异常路径。

#### 只影响预扣准确性（最终计费由 usage 修正）

**1. 样片（Draft）模式未折算**

`draft=true` 会经 metadata 原样下发，但预扣未乘折算系数（1.5 pro 无声 0.7 / 有声 0.6），
**预扣偏高约 43%**。usage 返回的是打折后的真实 token 数，结算会退回差额。

**2. 最低 token 用量限制未实现**

Seedance 2.0 系列 / 2.5 在含视频输入时有最低 token 用量兜底，本网关的估算可能低于该下界，
**预扣偏低**。usage 返回的是含兜底的真实值，结算会补扣。官方未公布公式，只有表格与计算器。

#### 已知取舍，暂不处理

**3. 成功但拿不到 usage 时保留最大预扣，且完全无声**

`settleTaskBillingOnComplete` 的第 3 个分支（无调整、保持预扣额度）不区分「预扣本来就准」
和「预扣是按上界猜的、但没等到 usage」。`duration = -1` 的 Seedance 2.5 按 30 秒预扣，
若那次终态响应没带 usage，用户就按 30 秒付费而实际可能只生成 5 秒，且日志里与正常结算
无法区分。

方舟官方成功响应必带 `usage.completion_tokens`，所以这是低概率异常路径。但要注意这个口子
是随「`duration = -1` 按区间上界预扣」一起变大的——此前按通用的 5 秒预扣，赌错也只差 5 秒。

修法（若将来要做）：在该分支判断「预扣按上界猜测 且 未取得 usage」，`logger.LogWarn` 并复用
`service/log_info_generate.go:attachQuotaSaturation` 落一个 `admin_info` 标记。

#### 配置正确即可规避

**4. 多数适配器没有计费估算**

实现了 `EstimateBilling` 的只有 ali / sora / gemini / vertex / doubao。kling / vidu /
hailuo / jimeng 会把 `duration` / `resolution` / `mode` 原样转发给上游却不参与计费。

**但配了 `video_token` 按秒价目表就不受影响**：那条路径走
`helper.ModelPriceHelperVideoToken`，按时长 × 分辨率精确计价，根本不经过 `EstimateBilling`。
只有把这些模型配成按量（token）计费时才会退化成「同一模型下 10s/1080p 与 5s/720p 同价」。

> 注：这四家的**时长同源**问题已修（时长的赋值统一移到 metadata 反序列化之后、取
> `RequestedOutputSeconds()`），这也是按秒计价能精确的前提。可灵还会把上游的
> `final_unit_deduction` 填进 `TotalTokens`，`RecalculateTaskQuotaByTokens` 里的按秒闸门
> 拦的正是这条真实路径——那个数字是上游的扣费单位，不是 token。

**5. `PerCallBilling` 无条件跳过结算**

`controller/relay.go` 中按次价模型置 `PerCallBilling=true`，`service/task_polling.go` 据此
直接返回，即使上游已返回 `usage` 也会丢弃。对「一次调用一个固定价」的配置意图而言这是
正确行为，只有当运营把一个本该按用量计费的模型误配成按次价时才成为问题。

**6. `AdjustBillingOnComplete` 全项目零实现**

`relay/channel/task/taskcommon/helpers.go` 的默认实现返回 0，11 个 task 适配器无一覆盖。
Seedance 有 token 重算覆盖、按秒档不需要修正，因此目前没有实际缺口；它限制的是将来想
基于上游终态返回的实际分辨率/时长做修正的场景。

**7. 级联（new-api → new-api）用量透传依赖上游**

`relay/relay_task.go:attachVideoTokenUsage` 把 `total_tokens` 回填到公开响应供下游取回，
但要求上游终态响应里本来就有 `total_tokens`。Seedance 链路满足；上游若是 vidu / hailuo /
jimeng / ali / sora / gemini / vertex 则没有，两级都停在各自的预扣估算上——而这几家正是
适合配按秒表的，配了就不依赖 usage。
